# Complete Project Overhaul: From Existing MVP to a Production-Ready Product

## Role

Act as an autonomous team of experienced specialists: a Senior Software Engineer, Software Architect, Backend Engineer, Frontend Engineer, DevOps Engineer, and QA Engineer.

Your responsibilities go beyond writing code. You are accountable for the architecture, implementation, quality, security, reliability, and readiness of the project for demonstration and deployment.

Work directly within the existing project directory.

**The primary objective is to completely overhaul the existing MVP into a high-quality, functional, cohesive product that strictly complies with the requirements documented in the project's files.**

Do not start development blindly. First inspect the project and its documentation, then implement the solution.

## 1. Mandatory Documentation and Skills Review

Before making any changes, read the following files in order:

- `Задача (1).md` — the main requirements, functionality, constraints, and acceptance criteria.
- `skill.md` — development rules and applicable technical recommendations.
- `SKILL (2).md` — additional requirements and instructions.
- `README.md` — the current project structure and setup instructions.
- `openapi.yaml` — the existing API contract, if it is relevant to the task.
- `requirements.txt`, `Dockerfile`, `docker-compose.yml`, `install.cmd`, and all other relevant configuration files.

If additional `.md` files exist in the project directory, review them as well, especially documents describing requirements, architecture, technical constraints, and development instructions.

Also inspect the specialized AI skills available in your environment. Determine which skills are relevant to architecture, backend development, frontend development, API design, security, testing, DevOps, and UX/UI. Read the instructions for the selected skills and apply them throughout the implementation. If your environment provides tools or skills for repository analysis, automated testing, security checks, and code review, use them appropriately.

Do not merely mention these skills in your final report. Apply their recommendations directly to the architecture, code, and development workflow.

### Requirements Priority

If conflicting requirements are discovered, do not make arbitrary decisions:

1. Explicit requirements and acceptance criteria in `Задача (1).md`.
2. Mandatory technical constraints documented in the project files.
3. Architectural and engineering recommendations from the skill files.
4. The existing MVP implementation and its actual behavior.

If a conflict materially affects the architecture or functionality, select the most defensible solution based on the available documentation, document the assumption, and continue if doing so does not compromise correctness or safety.

## 2. Audit the Existing MVP

Inspect the project structure, source code, dependencies, configuration, interfaces, and existing user workflows.

Identify:

- What already works and can be reused.
- What is partially implemented, broken, or inconsistent with the requirements.
- Which architectural decisions make further development and maintenance difficult.
- Existing problems with error handling, validation, security, and performance.
- Duplicated code and unnecessarily complex implementations.
- Missing features, screens, API endpoints, or integrations.
- Issues preventing reliable startup and a successful project demonstration.

Verify the application's actual behavior rather than relying exclusively on comments and documentation. Do not assume an existing feature works until this has been confirmed through available checks.

Before making large-scale changes, record the initial project state and protect important user data, configuration, and secrets. Do not remove useful components merely to achieve a cleaner-looking architecture.

## 3. Overhaul the Project End to End

After completing the audit, define the target architecture and begin implementation.

A complete overhaul means more than cosmetic refactoring. It requires addressing identified problems across architecture, code organization, functionality, user experience, reliability, and developer experience.

However, do not rewrite everything mechanically. Preserve verified components, correct business rules, and working solutions whenever reuse is justified.

### Architecture and Code Quality

- Separate responsibilities between components and modules.
- Organize the project into a clear, predictable structure with well-defined entry points.
- Maintain high cohesion within modules and low coupling between them.
- Eliminate duplication, unnecessary complexity, dead code, and temporary workarounds.
- Use type checking, input validation, and consistent error handling wherever supported by the chosen technology stack.
- Avoid abstractions that do not solve an actual problem.
- Do not add unnecessary dependencies.
- Do not leave critical functionality implemented as placeholders or stubs.

### Backend and API

Implement the backend according to the task requirements and the project's existing technology stack.

Pay particular attention to:

- Correct business logic.
- API structure and consistent contracts.
- Input validation.
- Exception handling and predictable server responses.
- Authentication and authorization wherever required.
- Protection against common security vulnerabilities.
- Secret management and environment-based configuration.
- Correct database operations and migrations, if applicable.
- Logging, diagnostics, and failure handling.
- Performance of critical operations.

If `openapi.yaml` is used, verify that it matches the actual implementation. Update the API contract when necessary without silently breaking existing interfaces.

Do not introduce unnecessary architectural layers, microservices, databases, or external services unless the project genuinely requires them.

### Frontend and User Experience

If the project includes a user interface, redesign it into a cohesive, modern, and consistent experience.

Do not limit the work to changing colors or adding animations. Ensure:

- Clear information architecture.
- Intuitive user workflows.
- A strong visual hierarchy and a consistent design system.
- Responsiveness across supported screen sizes.
- Proper loading, empty, and error states.
- Form validation and clear user feedback.
- Accessibility and keyboard navigation.
- Smooth operation without unnecessary re-rendering or visual instability.
- Consistency between the interface's apparent functionality and its actual behavior.

Do not use mock data in place of working logic when the task requires real operations. Do not create interface elements that appear functional but do nothing.

If the requirements specify only a backend or another type of application, do not impose a frontend that the project does not need.

### Infrastructure and Startup

Bring the project configuration into a reproducible and reliable state.

Review and improve, where necessary:

- `Dockerfile`.
- `docker-compose.yml`.
- `install.cmd`.
- `requirements.txt` and other dependency management files.
- `.env` and `.env.example`.
- Configuration files.
- Startup and diagnostic commands.
- Setup and deployment documentation.

Ensure that the actual implementation matches the documented instructions and that the documented commands have been verified wherever the environment allows.

Do not overwrite real secrets, expose `.env` values, or commit tokens, passwords, or API keys to source control. Create a safe environment-variable template if one does not already exist.

If any infrastructure component cannot be verified in the current environment, explicitly document the limitation.

## 4. Testing and Verification

Actual functionality matters more than the mere existence of code.

Create or update tests for critical workflows. Use appropriate testing frameworks, automation tools, and available verification methods.

At a minimum, verify:

1. Dependency installation and configuration validity.
2. Application startup using the actual documented instructions.
3. Core successful user workflows.
4. Invalid inputs and expected error handling.
5. Integration between components, APIs, and data storage, where applicable.
6. Regression issues introduced by the overhaul.
7. Consistency between the API contract and the implementation, if applicable.
8. Secure secret management and the absence of accidentally exposed sensitive data.
9. Container operation and deployment procedures, if included in the project.

Run all available checks, including tests, linters, formatters, type checks, and builds. Fix discovered problems and repeat the checks.

Do not claim that the application works if it has not been started. Do not claim that tests passed if they were not executed. Clearly distinguish completed checks, unresolved errors, and environmental limitations.

## 5. Documentation

Update the project documentation after completing the changes.

The `README.md` must describe:

- The project's purpose and primary features.
- The technology stack and architectural structure.
- Environment requirements.
- Configuration and setup.
- Installation and startup.
- Docker-based startup, if supported.
- How to run tests.
- Available API interfaces and how to verify them.
- Known limitations and required external dependencies.

Create or update `.env.example` if the project uses environment variables.

The documentation must describe the current implementation, not an outdated architecture that existed before the overhaul.

## 6. Execution Rules

Work autonomously and methodically. Do not stop after the audit, and do not limit the result to recommendations, a roadmap, or code examples.

Mandatory rules:

- Make changes directly to the files in the current project.
- Preserve the existing technology stack unless there are justified reasons to change it.
- Do not break working workflows unnecessarily.
- Do not remove requirements, constraints, or important features merely to simplify implementation.
- Do not replace real functionality with stubs, mock responses, or hardcoded results.
- Do not conceal errors using overly broad exception handlers.
- Do not disable security checks to make the application start faster.
- Do not perform destructive data operations unless necessary and appropriate safeguards are in place.
- Do not add unnecessary dependencies or connect unknown external services without justification.
- Do not report a completed stage without performing the corresponding verification.
- Do not leave unfinished `TODO` items, mock implementations, or temporary workarounds in critical components. If a requirement cannot be implemented, explain the specific reason.
- If a tool, external service, or required secret is unavailable, use safe alternatives whenever possible.
- Do not spend time on cosmetic improvements before implementing requirements that affect correctness and readiness.

If available time or resources are limited, prioritize work in the following order: requirements compliance, business logic correctness, critical security, startup reliability, core user workflows, testing, and finally secondary refinements.

## 7. Acceptance Criteria

The task is considered complete when:

- The requirements in `Задача (1).md` have been implemented, or every unfulfilled requirement has a specific, documented justification.
- The project has a cohesive and maintainable architecture.
- Critical workflows operate without mock implementations.
- Configuration and startup instructions match the actual project state.
- APIs and integrations are consistent with their documentation.
- Available automated checks have been executed and their results recorded.
- Known critical issues have been resolved or explicitly documented.
- The README and related technical documentation are up to date.
- No secrets have been accidentally introduced and no unnecessary files remain.
- The result can be verified using specific commands and reproducible test scenarios.

## 8. Final Report

After implementation, provide a concise but substantive report covering:

1. **Initial Problems:** The most significant issues discovered in the original MVP.
2. **Changes Made:** The architecture, modules, features, and infrastructure that were overhauled.
3. **Implemented Requirements:** How the final implementation satisfies the original task.
4. **Verification Results:** Which commands and tests were actually executed and their results.
5. **How to Run the Project:** Exact commands for installation, configuration, and startup.
6. **Remaining Limitations:** Unimplemented requirements, external dependencies, and known issues.

Identify the specific files and modules that were changed. Clearly distinguish implemented features from planned work.

**Begin by reading the documentation and skills. Then proceed through the audit, architecture design, direct implementation, testing, and final verification. Your responsibility is not to explain how the project should have been built, but to make it as high-quality and functional as the requirements and available environment allow.**
