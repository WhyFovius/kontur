# Контур — аналитика риска оттока

Веб-панель и REST API для оценки риска непродления услуг хостинга и приоритизации работы команды удержания. Приложение принимает JSON-снимок аккаунтов, услуг и транзакций, рассчитывает объяснимый скор риска и денежную оценку потерь, а настройки модели хранит в SQLite по умолчанию или в PostgreSQL при заданном `DATABASE_URL` — изменение весов в панели пересчитывает рейтинг без перезагрузки и переживает перезапуск.

## Быстрый старт

Нужен Docker Desktop / Docker Engine с Compose v2.

```bash
cp .env.example .env          # в Windows PowerShell: Copy-Item .env.example .env
# укажите в .env уникальный ADMIN_PASSWORD
docker compose up --build -d
```

Откройте **http://localhost:8000** и войдите под `ADMIN_USERNAME` / `ADMIN_PASSWORD` из `.env`.

> Порт по умолчанию — **8000** (не 8080). Чтобы публиковать на другом порту хоста, задайте в `.env` например `PORT=8080` — тогда панель будет на http://localhost:8080.

При первом запуске с пустой базой приложение само создаёт восемь синтетических демонстрационных аккаунтов — панель не будет пустой. В конфигурации по умолчанию SQLite-база лежит в `data/churn.db` на хосте и сохраняется между перезапусками контейнера. Для PostgreSQL задайте `DATABASE_URL` (см. «Хранение данных: SQLite и PostgreSQL» ниже); существующая SQLite-база при этом автоматически не переносится.

Остановка и логи:

```bash
docker compose ps
docker compose logs -f churn-risk
docker compose down
```

## Возможности

- **Рейтинг клиентов**: скор 0–100, уровни риска (низкий / средний / высокий / без оценки), человекочитаемые причины, фильтр по уровню риска, пагинация и сортировка по ID, email, балансу, сумме пополнений и скору — по возрастанию и по убыванию.
- **Карточка клиента**: услуги, балансы, вклад каждого признака в скор, выручка и потенциальная потеря.
- **Модель в панели**: веса шести признаков меняются слайдерами и применяются без перезагрузки страницы; сохраняются в базе данных и действуют после перезапуска.
- **Realtime-монитор риска**: сервер сравнивает свежий анализ с предыдущим состоянием, сохраняет эпизоды в базе данных и публикует новые события по SSE. Критичным считается скор от 80; отдельно отслеживаются ожидание оплаты, окончание услуги в ближайшие 72 часа, нехватка денег, рост скора и скачки портфельных потерь. В панели события показывает Aéza-тян в виде «мыслей» и inbox с папками «Непрочитанные» и «Прочитанные».
- **Live-монитор / Dev Panel**: отдельная страница для проверки realtime-цепочки. DEMO-генератор создаёт события шести сценариев, сервер пересчитывает риск на базе существующей модели и отдельного DEMO-модификатора активности, сохраняет событие и расчёт, применяет anti-spam и публикует результат в replayable SSE. Есть симулятор потока, Chaos Mix, фильтры, детали события и Flight Recorder клиента. DEMO-данные изолированы и сбрасываются одной кнопкой, live-снимок не изменяется. API/STREAM-адаптеры LIVE честно показываются как неподключённые, пока не заданы и не реализованы реальные источники.
- **Autopilot реакций**: значимое событие само выбирает шаблон и канал: сначала указанная соцсеть (Telegram/WhatsApp/VK), иначе email. Текст подставляет риск и следующее действие из Rescue Queue, включая точную сумму пополнения. В DEMO запись получает статус `simulated_sent` и не уходит наружу; для LIVE нужен реальный провайдер доставки.
- **Очередь спасения**: backend priority engine ранжирует клиентов не только по скору, но и по деньгам, дедлайну и выполнимости действия. Для каждого клиента API возвращает следующее действие, точную сумму пополнения, прогноз скора после действия, ценность спасения и ценность в день.
- **Денежная оценка риска** с учётом стоимости услуг, доступного баланса и категории риска.
- **Загрузка снимков** из панели (файл или drag-and-drop) и по API: полная валидация и атомарная замена данных — битый снимок не трогает текущие данные.
- **Аутентификация обязательна**: пароль администратора, опционально OpenID Connect (SSO), для программных клиентов — HTTP Basic. Без входа бизнес-данные недоступны.
- **Prometheus-метрики** из того же расчёта, что и панель.
- Панель автообновляет данные каждые 10 секунд; светлая и тёмная темы, адаптивная вёрстка, клавиатурная навигация, поддержка `prefers-reduced-motion`.

## Модель риска

Скор — детерминированная объяснимая эвристика для приоритизации обращений, **не** обученная вероятность оттока. Каждый признак — булев сигнал с настраиваемым весом:

| Признак (`key`) | Сигнал | Вес по умолчанию |
| --- | --- | ---: |
| `expiring_without_autoprolong` | Услуга скоро заканчивается и у неё нет автопродления | 25 |
| `insufficient_funds` | Доступного баланса не хватит на ближайшее продление | 25 |
| `prolong_wait` | Есть услуга в статусе «ожидает оплаты» | 25 |
| `failed_transactions` | Были незавершённые/неудачные платежи | 12 |
| `deleted_services` | Клиент уже удалял услуги | 8 |
| `balance_pressure` | Месячная стоимость услуг велика относительно истории пополнений | 5 |

Скор = 100 × (сумма весов активных сигналов) / (сумма всех положительных весов). Пороги: **≥ 65 — высокий**, **≥ 35 — средний**, ниже — низкий. Аккаунт без услуг и транзакций получает `unrated`. Подписи причин генерируются из тех же сигналов — скор всегда можно объяснить.

**Денежная оценка.** Месячная выручка клиента — стоимость активных и приостановленных услуг, приведённая к месяцу по `paymentTerm`. Потенциальная потеря на горизонте 3 месяцев:

```
estimatedLoss = max(0, 3 × месячная выручка − доступный баланс) × коэффициент риска
```

Коэффициент риска: высокий — 0,80; средний — 0,45; низкий — 0,15. Доступный баланс = `balance` + `bonusBalance` (бонус учитывается только при нормализованном `bonusState = true`). При импорте boolean-поля принимают не только JSON `true/false`, но и `1/0`, `yes/no`, `on/off`, `active/inactive` и небольшие status-объекты вида `{"enabled": "yes"}`. Все суммы в API и снимках — целые **евроценты**; панель форматирует их в евро.

**Прогноз.** `churnForecast` считает услуги, которые могут не продлиться к горизонтам 0/7/14/21/30 дней (ожидающие оплаты + истекающие без автопродления). Отдельный эндпоинт динамики раскладывает факт и прогноз по бакетам 90 дней назад/вперёд; ожидаемые непродления взвешены теми же коэффициентами риска.

## Панель

Четыре страницы рабочего пространства:

- **Обзор** — KPI портфеля, единственная «Очередь спасения», концентрация выручки по клиентам, локально выбираемые сегменты риска, scrub-инспектор потока по срокам окончания с топ-клиентами сегмента, калькулятор спасённой выручки и качество данных.
- **Клиенты** — рейтинг с фильтрами и сортировкой, раскрывающиеся карточки с разбором скора, сохранённые виды (хранятся локально в браузере).
- **Модель риска** — слайдеры весов (пересчёт на лету, сохранение по кнопке), локальный what-if сценарий без записи на сервер.
- **Live-монитор** — Dev Panel DEMO-событий, источники и пороги, графики сохранённых расчётов, Event Feed, история клиента, шаблоны реакций и outbox.

Aéza-тян остаётся постоянным realtime-инбоксом поверх страниц: по умолчанию открывает папку «Непрочитанные», фильтрует критические события, ставит штамп «ПРОЧИТАНО» и переносит уведомление в отдельную папку «Прочитанные», откуда его можно вернуть обратно.

Интерфейс — React 19 + TypeScript + Framer Motion, дизайн-система Material Design 3 Expressive в фирменном стиле Aéza. Собранный бандл коммитится в `static/app` и раздаётся FastAPI, поэтому на сервере Node не нужен; если бандла нет, отдаются легаси-страницы из `templates/` и `static/login.html`.

## Архитектура

```
Снимок JSON ─► нормализация/валидация ─► БД: JSON + типизированные факты услуг
                                                  │
Веса из панели ─► PATCH /model/settings ─► БД (settings + model_version)
                                                  ▼
                         prepared source: аккаунты + ServiceFact/агрегаты транзакций
                                                  ▼
                              analyze_prepared(): скор → деньги
                                                  ▼
                     API рейтинга · сводка · динамика · /metrics · панель
```

При замене снимка факты услуг (статус, цена, месячная выручка, автопродление и epoch-время окончания/удаления) материализуются в отдельные колонки; транзакции для скоринга агрегируются в SQL до `total` и флага неудачного платежа. Поэтому изменение только весов не требует заново парсить даты и все транзакции.

Кэши разделены по смыслу: prepared-снимок кэшируется по `snapshot_version`, готовый анализ — по паре `(snapshot_version, model_version)`. Тяжёлый пересчёт выполняется вне event loop и защищён single-flight; при обычном истечении TTL (`ANALYSIS_CACHE_TTL_SECONDS`, по умолчанию 10 секунд) запросы получают последний полный анализ, пока один фоновый поток готовит свежий. Смена снимка или весов считается синхронно в worker-потоке — устаревшие веса пользователю не отдаются.

DEMO/LIVE-события идут отдельным, но связанным потоком:

```
Источник → нормализованное событие → серверный расчёт риска → history в БД
                                      ├─► значимое? → inbox Aéza-тян / SSE
                                      └─► шаблон реакции → канал клиента → outbox
```

Для существующего клиента базовый скор берётся из текущего prepared-анализа; DEMO-активность хранится как отдельный модификатор и никогда не переписывает аккаунты, услуги или транзакции снимка.

### Формат снимка

```json
{
  "accounts": [{"id": 42, "email": "client@example.org", "balance": 8500, "bonusBalance": 300, "bonusState": true, "totalReplenished": 42000}],
  "services": [{"id": "s-1", "accountId": 42, "name": "Виртуальный сервер", "status": "active", "price": 2400, "paymentTerm": "month", "autoprolong": false, "expiresAt": "2026-11-02T00:00:00Z"}],
  "transactions": [{"id": "t-1", "accountId": 42, "amount": 10000, "type": "order", "status": "performed"}]
}
```

- Деньги — целые неотрицательные евроценты (`balance`, `withdrawBalance`, `bonusBalance`, `totalReplenished`, `price`, `amount`).
- Boolean-поля `bonusState` и `autoprolong` нормализуются из `true/false`, `1/0`, `yes/no`, `on/off`, `active/inactive`, `enabled/disabled`, русских форм и status-объектов с `enabled`/`active`/`value`/`state`/`status`; неизвестное значение по-прежнему отклоняет весь снимок.
- Необязательные контакты аккаунта для Autopilot: `telegram`, `whatsapp`, `vk` или объект `socials` с теми же ключами. Если соцсетей нет, используется `email`; публичный API клиентов эти контакты не раскрывает.
- Статусы услуг: `active`, `suspended`, `prolong_wait`, `deleted`, `blocked` (`suspended` продолжает давать выручку). Периоды оплаты: `hour`, `week`, `month`, `quarter_year`, `half_year`, `year`.
- Для удалённых услуг поле `deletedAt` (алиасы `deleted_at`, `removedAt`) задаёт дату удаления для графика факта; без него используется `expiresAt`.
- Допускаются алиасы коллекций (`users`/`customers`/`clients` вместо `accounts`, `subscriptions` вместо `services`, `payments` вместо `transactions`) и полей (`_id`, `email_address`, `account_id`/`userId`/`customerId`, `withdraw_balance`, `bonus_balance`, `total_replenished`, `payment_term`/`billing_period`, `auto_renew`/`autoRenew`, `expires_at`/`expiration_date`, `removed_at`). Одновременно заданные конфликтующие алиасы отклоняют весь снимок.
- Снимок можно передать либо напрямую, либо в единственной обёртке `data` или `snapshot`. Услуги и транзакции также могут быть вложены в аккаунт (`accounts[].services` / `accounts[].transactions`); в этом случае владельцем считается сам аккаунт, а явный `accountId` во вложенной записи запрещён.
- Статусы транзакций: `performed` и `not_performed`; типы: `prolong` и `order`.
- Тело запроса ограничено 32 MiB. После нормализации допускается не более 100 000 аккаунтов, 500 000 услуг и 1 000 000 транзакций. Некорректный снимок отклоняется целиком до удаления текущих данных.

## Хранение данных: SQLite и PostgreSQL

### SQLite по умолчанию

Если `DATABASE_URL` пуст, используется файл из `DATABASE_PATH` (в Docker — `/app/data/churn.db`). Подключение явно настраивает WAL, `synchronous=NORMAL`, `busy_timeout=15000` мс, page cache 16 MiB, `temp_store=MEMORY` и `wal_autocheckpoint=1000`; при штатном завершении приложения выполняется `wal_checkpoint(TRUNCATE)`.

`WAL + NORMAL` — осознанный баланс скорости и надёжности: транзакции атомарны и согласованны, но при внезапной потере питания последние закоммиченные транзакции теоретически могут откатиться. Если такая потеря недопустима, задайте `SQLITE_SYNCHRONOUS=FULL`. Для резервной копии останавливайте приложение и копируйте базу после checkpoint либо используйте online backup средствами SQLite; копирование только `.db` при живом `-wal` может дать неполную копию.

SQLite остаётся однохостовым хранилищем с одним писателем. Несколько Uvicorn worker-процессов не рекомендуются для SQLite: каждый процесс будет держать собственный кэш анализа в памяти и конкурировать за единственного писателя. Базу нельзя размещать на сетевой файловой системе.

### PostgreSQL через `DATABASE_URL`

Для внешнего PostgreSQL достаточно URL вида:

```dotenv
DATABASE_URL=postgresql://kontur:<url-encoded-password>@db.example.com:5432/kontur
DATABASE_POOL_MAX=10
DATABASE_CONNECT_TIMEOUT_SECONDS=5
```

Поддерживаются схемы `postgresql://` и `postgres://`. Схема создаётся идемпотентно при старте; если новая база ещё не инициализирована, в неё загружается тот же демонстрационный снимок. Подключения PostgreSQL берутся из ограниченного пула процесса. При нескольких worker-процессах общий лимит подключений равен `workers × DATABASE_POOL_MAX`, а кэш анализа по-прежнему дублируется в каждом процессе.

Для встроенного Compose-профиля задайте в `.env` согласованные `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD` и `DATABASE_URL`, затем запустите сначала базу:

```bash
docker compose --profile postgres up -d postgres
docker compose --profile postgres ps   # дождитесь healthy
docker compose up --build -d churn-risk
```

Автоматического переноса данных SQLite ↔ PostgreSQL нет: это разные базы. Снимок можно заново загрузить через `PUT /api/v1/source/snapshot`, но веса, сессии, история уведомлений и realtime-события таким способом не переносятся.

Существующая SQLite-база обновляется на месте: при первом старте новой версии добавляются типизированные колонки фактов и индексы, значения backfill-ятся из сохранённого JSON, после чего выставляется `snapshot_facts_version=1`. Миграция не удаляет аккаунты, услуги, транзакции, настройки или сессии.

## Локальная разработка

Backend (рекомендуется Python 3.12):

```bash
python -m venv .venv
# Linux/macOS: source .venv/bin/activate
# Windows PowerShell: .\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
ADMIN_USERNAME=admin ADMIN_PASSWORD='set-a-unique-local-password' \
  uvicorn code:app --host 0.0.0.0 --port 8000
```

В Windows PowerShell переменные задаются через `$env:ADMIN_USERNAME = "admin"` и `$env:ADMIN_PASSWORD = "..."`. Для другого порта используйте, например, `uvicorn code:app --port 8080`.

Frontend:

```bash
npm --prefix frontend ci
npm --prefix frontend run build
```

Результат пишется в закоммиченный `static/app`, поэтому production-образу Node не нужен. Для разработки интерфейса можно запустить `npm --prefix frontend run dev`: Vite на порту 5173 проксирует `/api` и `/health` на Uvicorn `127.0.0.1:8000`.

## Аутентификация: пароль, OIDC и Basic

По умолчанию работает администратор из `ADMIN_USERNAME`/`ADMIN_PASSWORD`; попытка входа ограничена восемью неудачами за 15 минут для одного адреса. Для внешнего identity provider задайте `OIDC_ISSUER`, `OIDC_CLIENT_ID`, при необходимости `OIDC_CLIENT_SECRET`, `OIDC_REDIRECT_URI`, `OIDC_SCOPES`, `OIDC_PROVIDER_NAME` и необязательный allowlist `OIDC_ALLOWED_USERS`.

В провайдере зарегистрируйте redirect URI `https://<ваш-хост>/api/v1/auth/oidc/callback`. Поток — Authorization Code с PKCE (S256); `state`, `nonce` и `code_verifier` живут на сервере 10 минут, ID-токен проверяется по JWKS (подпись, `iss`, `aud`, `exp`, `nonce`), после чего создаётся та же серверная сессия, что и при парольном входе. Парольный вход остаётся fallback, а программные клиенты могут использовать HTTP Basic. За HTTPS задавайте `COOKIE_SECURE=true`.

## Расширение модели

Чтобы добавить сигнал:

1. Добавьте метаданные `Feature(key, label, default_weight)` в `FEATURES` в `churnrisk/domain.py`; панель и валидация весов подхватят ключ автоматически.
2. Если сигналу нужны новые поля услуги или транзакции, расширьте `ServiceFact`/`TransactionFact`, материализацию в `replace_snapshot` и загрузку в `load_prepared_source`; для старых баз добавьте колонку и backfill в миграцию storage.
3. Вычислите булев сигнал один раз в `analyze_prepared`, включите его вес в скор, добавьте значение в `features` и человекочитаемую причину.
4. Если по сигналу есть конкретное действие удержания, учтите его в Rescue Queue и, при необходимости, в `alert_candidates`.
5. Покройте тестами точный скор, причину, граничные даты/суммы и сохранение нового веса через API.

## Ограничения и эксплуатационные замечания

- Скор — объяснимая эвристика приоритизации, а не обученная вероятность и не причинная uplift-модель. ML имеет смысл только после накопления исторических исходов продления/оттока и проверки калибровки.
- Кэш анализа находится в памяти процесса. PostgreSQL решает совместный доступ к данным и конкурентную запись, но не делает кэш общим между репликами; каждая реплика платит свою память и может до TTL отдавать собственный последний полный анализ.
- OIDC не добавляет ролей внутри панели: вошедший администратор или пользователь из allowlist получает полный доступ.
- `GET /metrics` публичен и не содержит персональных данных, но раскрывает агрегаты портфеля; при необходимости ограничивайте его на reverse proxy или сетевом уровне.
- LIVE-адаптеры и реальная доставка Autopilot-сообщений не подключены: DEMO честно помечает отправки как `simulated_sent`.
- Точность сроков, выручки и прогноза зависит от корректности дат, статусов и периодов оплаты в загружаемом снимке.
